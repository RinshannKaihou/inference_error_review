[Bug]: Quark FSE compatibility check matches `shared_expert_gate`, silently disabling fused shared experts on Qwen MoE MXFP4
## Summary

`is_shared_expert_quant_fse_compatible` decides whether AITER fused shared experts (FSE) may run by searching the **entire** Quark `exclude` list for the substring `shared_expert`:

https://github.com/vllm-project/vllm/blob/main/vllm/model_executor/layers/quantization/utils/config_utils.py#L106-L111

```python
is_compatible = not any(
    "shared_expert" in str(entry)
    for entry in quant_config.quant_config["exclude"]
)
if not is_compatible:
    return False, f"Quark excludes shared experts at {shared_expert_prefix}"
```

That substring also matches `mlp.shared_expert_gate`, which is a **different module**: the `hidden_size -> 1` router gate that scales the shared expert's output. It is BF16 by design (quantizing a 1-column projection is pointless), so every Qwen MoE Quark checkpoint lists it in `exclude` — including checkpoints whose shared-expert projections are fully MXFP4.

The result is that FSE is refused on exactly the checkpoints it was enabled for. Nothing fails and accuracy is unchanged; the shared expert simply runs unfused, costing the FSE speedup on ROCm, with only a per-MoE-layer startup warning:

```
VLLM_ROCM_USE_AITER_FUSION_SHARED_EXPERTS is enabled but cannot be enabled:
Quark excludes shared experts at model.layers.0.mlp.shared_expert.
```

## Regression

Introduced in #51695, which moved Qwen off its own local check onto the shared helper. The previous Qwen check matched `"shared_expert."` **with the trailing dot**, which only matched real projections (`shared_expert.down_proj`) and correctly ignored the `shared_expert_gate` sibling:

```python
# removed in #51695, vllm/model_executor/models/qwen3_next.py
return not any("shared_expert." in str(e) for e in exclude)
```

The dot appears to have been dropped so one substring could cover both the Qwen singular `shared_expert.` and the DeepSeek/GLM plural `shared_experts.`. The test added in that PR only exercises the plural naming and never a `shared_expert_gate` sibling, which is why CI did not catch it.

## Reproduction

No GPU needed — the check is a pure function of `config.json`. Using a public checkpoint:

```python
import json
from huggingface_hub import hf_hub_download

path = hf_hub_download("amd/Qwen3.5-397B-A17B-MoE-MXFP4", "config.json")
exclude = json.load(open(path))["quantization_config"]["exclude"]

matches = [e for e in exclude if "shared_expert" in e]
print(len(matches), "entries match the current check, e.g.", matches[:2])
print("any real shared-expert projection excluded:",
      any("shared_expert." in e for e in exclude))
```

```
61 entries match the current check, e.g. ['model.layers.0.mlp.shared_expert_gate', 'model.layers.1.mlp.shared_expert_gate']
any real shared-expert projection excluded: False
```

Every match is the router gate; not a single shared-expert projection is excluded. The current check nevertheless reports incompatible and FSE is disabled.

## Impact

Evaluated by building a real `QuarkConfig` from each checkpoint (weights mapper applied, `packed_modules_mapping` populated as the loader does) and calling the gate:

| Checkpoint | before #51695 | current `main` | correct |
| --- | --- | --- | --- |
| `amd/Qwen3.5-397B-A17B-MoE-MXFP4` (public) | enabled | **disabled** | enabled |
| `amd/Qwen3.8-2.4T-A95B-MoE-MXFP4` | enabled | **disabled** | enabled |
| `amd/Qwen3.8-2.4T-A95B-Quark-MXFP4` (public) | disabled | disabled | disabled — shared expert genuinely BF16 |

The last row is the true positive the check exists for, and it must keep working: that checkpoint really does exclude `shared_expert.{gate,up,down}_proj`.

## Proposed fix

Ask whether the shared expert's **own projections** are excluded, instead of substring-scanning the list. `should_ignore_layer` already answers exactly this question — it is what `QuarkConfig.get_quant_method` uses — and it handles exact names, `re:`/glob patterns, and expands fused names such as `gate_up_proj` into the `gate_proj`/`up_proj` shards the checkpoint stores. Being scoped to one module, a sibling cannot trigger it. This also matches the DeepSeek-V4 branch a few lines above, which already scopes with `startswith(shared_expert_prefix)`.

```diff
     if isinstance(quant_config, QuarkConfig):
+        from vllm.model_executor.layers.quantization.quark.utils import (
+            should_ignore_layer,
+        )
+
         # TODO: layer_type_quant_config is not taken into account here.
         assert "exclude" in quant_config.quant_config
         assert "global_quant_config" in quant_config.quant_config
 
-        is_compatible = not any(
-            "shared_expert" in str(entry)
-            for entry in quant_config.quant_config["exclude"]
-        )
-        if not is_compatible:
-            return False, f"Quark excludes shared experts at {shared_expert_prefix}"
+        # Ask whether the shared expert's own projections are excluded rather
+        # than searching the exclude list for the substring "shared_expert".
+        # Sibling modules contain that substring while saying nothing about the
+        # shared expert: every Qwen MoE checkpoint excludes
+        # `mlp.shared_expert_gate`, a 1-wide router gate that is BF16 by design.
+        excluded = [
+            projection_name
+            for projection_name in projection_names
+            if should_ignore_layer(
+                f"{shared_expert_prefix}.{projection_name}",
+                ignore=quant_config.quant_config["exclude"],
+                fused_mapping=quant_config.packed_modules_mapping,
+            )
+        ]
+        if excluded:
+            return False, (
+                f"Quark excludes shared-expert {', '.join(excluded)} at "
+                f"{shared_expert_prefix}"
+            )
```

`projection_names` is already a parameter and is already used further down, so this introduces no new inputs. With the patch applied, the three checkpoints above return enabled / enabled / disabled, and the refusal message becomes specific: `Quark excludes shared-expert gate_up_proj, down_proj at model.layers.0.mlp.shared_expert`.

Restoring the trailing dot would also work and is a one-character change, but it leaves the same trap for the next module named `shared_expert_*`, and it still relies on guessing names rather than asking whether a module is excluded.

I am happy to open a PR with this plus a regression test covering a checkpoint that excludes `shared_expert_gate` while quantizing the shared-expert projections.

## Environment

Working build (FSE enabled): `0.27.2rc1.dev150+g311b3513a`, ROCm, MI355X (gfx950), Qwen3.8/Qwen3.5 MoE MXFP4, `VLLM_ROCM_USE_AITER=1 VLLM_ROCM_USE_AITER_FUSION_SHARED_EXPERTS=1`. Regression confirmed present on `main` as of today.
