NVFP4 MoE silently folds an uninitialised activation scale for weight-only checkpoints (zeroes every expert)
### Summary

`ModelOptNvFp4FusedMoE` accepts a **weight-only** NVFP4 checkpoint (one with
`"input_activations": null` and no `input_scale` tensors) and then folds an
**uninitialised** parameter into the dequantisation alphas. Every expert output is
multiplied by zero, the model degenerates to a single repeated token, and there is
no error and no warning.

The NVFP4 *linear* methods refuse the same checkpoint explicitly. The inconsistency
is the bug.

### Detail

`ModelOptNvFp4FusedMoE.create_weights` registers:

```python
w13_input_scale = PerTensorScaleParameter(
    data=torch.empty(global_sf_num_experts, dtype=torch.float32), ...)
```

A weight-only checkpoint never fills it. `process_weights_after_loading` passes it
straight into the kernel-format conversion, where it becomes both the
dequantisation alpha (`g1_alphas = weight_scale_2 * input_scale`) and the
activation global scale (`a1_gscale = 1.0 / input_scale`).

Observed value in practice: **0.0**. So `g1_alphas` is 0 for every expert, the
whole mixture of experts contributes nothing, and the model runs on attention plus
the shared expert alone.

Both NVFP4 linear methods guard this case:

```python
if not self.quant_config.is_checkpoint_nvfp4_serialized:
    raise ValueError("NVFP4 quantization was selected, "
                     "dynamic quantization is not supported.")
```

and there is a dedicated weight-only linear path
(`ModelOptNvFp4W4A16LinearMethod`). There is **no W4A16 equivalent for MoE** and no
such guard.

### Why this reads as architecture-specific but is not

Reports of this symptom on GB10 / DGX Spark conclude "FLASHINFER_CUTLASS MoE
produces silent garbage on GB10, use marlin". Marlin dequantises the weights and
runs an ordinary bf16 GEMM, so it never consumes an activation scale and never
reaches this code path. The trigger is the checkpoint, not the GPU.

A standalone harness driving `flashinfer.fused_moe.cutlass_fused_moe` directly on
GB10 shows the kernel itself is correct when fed properly, matching an fp32
reference at `cos = 0.9969` (fp4 noise). It also confirms vLLM's
`reorder_w1w3_to_w3w1` and its alpha convention are both correct, so the kernel and
the layout are not at fault.

### Reproduce

Any weight-only modelopt NVFP4 MoE checkpoint. Example:
[`LibertAIDAI/GLM-5.3-Flash-NVFP4`](https://huggingface.co/LibertAIDAI/GLM-5.3-Flash-NVFP4)

```
*.weight_scale   : 37152 tensors
*.weight_scale_2 : 37152 tensors
*.input_scale    : 0 tensors
quantization_config: {"input_activations": null, "quant_algo": "NVFP4", ...}
```

Serve with `--moe-backend flashinfer_cutlass`: every prompt returns one token
repeated to the limit. Serve with `--moe-backend marlin`: output is correct.

### Suggested fix

Any of, in rough order of preference:

1. Add a weight-only MoE path that derives the activation scale dynamically.
   SGLang does this, which is why it serves the same checkpoint correctly.
2. Apply the guard the linear methods already have, so the checkpoint is refused
   loudly rather than served wrongly.
3. At minimum, initialise the parameter to 1.0 instead of `torch.empty`. The
   activation scale cancels analytically (activations are quantised with
   `1/input_scale` and dequantised with an alpha proportional to `input_scale`), so
   it only affects how well activations fit fp4's range through the e4m3 block
   scales. That turns a silent numerical fault into, at worst, a suboptimal one.

### Environment

Reproduced on 2× GB10 (sm_121), TP=2, vLLM `0.1.dev20051+g487ecf187`, flashinfer
0.6.17. Analysis and the standalone MoE harness:
https://github.com/Libertai/glm53-flash-vllm-gb10
