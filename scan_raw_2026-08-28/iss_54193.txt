[Bug]: KV offloading connector: finished-request store watermark includes a KV slot never written by any forward pass (silent cross-request poisoning with offload_prompt_only=False)
### Your current environment

Observed on `main` (also present in our fork based on f561eca). Scheduler-side logic only; independent of backend/hardware. Found while validating decode-side offloading (`offload_prompt_only=False`) for a hybrid-attention model in production, but the mechanism is model-agnostic.

### 🐛 Describe the bug

**Summary:** when a request finishes, the offloading connector's store watermark is `req.num_tokens`, which includes the final sampled token — a position whose KV-cache slot was **never written by any forward pass**. If the generation ends exactly on a block boundary, that block is offloaded as "complete" under its content hash, and any later request that reuses the same content loads a block whose last KV slot is garbage. Silent cross-request KV poisoning: no crash, no error, only degraded continuations.

**Where:** `vllm/distributed/kv_transfer/kv_connector/v1/offloading/scheduler.py`, in the per-step store-jobs walk:

```python
if req.status is RequestStatus.FINISHED_ABORTED:
    num_tokens_after_batch = req.num_computed_tokens
elif req.is_finished():
    num_tokens_after_batch = req.num_tokens          # <-- includes the sampled token
```

(currently around line 1266 on `main`; the `FINISHED_ABORTED` branch above it is correct.)

**Mechanism:**

1. A request finishes at `num_tokens = n`. The token at position `n-1` (EOS / stop token) was *sampled* from the forward pass of position `n-2`; position `n-1` itself is never forwarded, so its KV slot is never written.
   - Plain decode: the slot holds stale/uninitialized values.
   - **Speculative decoding makes it worse:** the slot holds the KV of the first *rejected* draft token — in-distribution values, so nothing looks wrong even if you inspect the cache.
2. With `offload_prompt_only=False`, `_calc_num_offloadable_tokens` does not clamp to the prompt, so the watermark `n` covers the final block. If `n` is block-aligned, the final block is considered complete and gets stored under its content hash. The hash is computed over token **ids**, which are all valid — including the sampled token — so the stored block is fully addressable.
3. A later request whose token stream matches that content — the standard multi-turn pattern of re-sending the full transcript (the sampled stop token is part of the assistant message) — gets an offload HIT and loads the block. The last slot of the loaded block is the never-written garbage, now serving as real KV for a *different* request.

**Trigger conditions:** `offload_prompt_only=False` (opt-in) × finish landing exactly on a block boundary (~1/block_size of requests, so routine at scale) × content reuse across requests (multi-turn / shared transcripts). With the default `offload_prompt_only=True` the clamp to `num_prompt_tokens` keeps the bug dormant (every prompt position is computed by prefill, so the prompt side is safe).

**Why it's hard to catch:** the poisoned slot is one token's KV out of a full block; retrieval-style tests (needle) pass, and with spec decode the values are statistically plausible. It only shows up as occasional quality degradation of continuations that rewarm across the poisoned boundary — which is exactly the workload decode offloading exists for.

**Suggested fix** (what we run in production):

```python
elif req.is_finished():
    # Drained frontier: the final sampled token's KV slot is never written
    # by a forward pass (with spec decode it holds the first rejected
    # draft's KV). max() keeps the full prompt, which prefill did compute.
    num_tokens_after_batch = max(req.num_prompt_tokens, req.num_tokens - 1)
```

Unit-test contract that pins it: a request finishing exactly at a block boundary must store nothing for the final block (and, one token past the boundary, must store only up to the boundary). Existing tests that expect the final block to be stored at finish encode the poisoning behavior and need the corresponding adjustment.

Happy to send a PR with the fix + tests if the maintainers agree with the analysis.
