### 55346 [closed] ttnn.argmax: FLOAT32 never selects a NaN and BFLOAT16 lets a later +0 beat an earlier -0, so the two dtypes return different indices and both differ from torch
**Component / Area:** ttnn reduction, `argmax` reader kernels and the shared float comparators

**Issue Type:** Bad Outputs

## Summary

The non-SFPU argmax paths (single core, multicore, tile-layout) compare raw bit patterns through two helpers:

- [float32.h#L18-L61](https://github.com/tenstorrent/tt-metal/blob/9fa00fce13cda1538f0130695576408ff5b05665/tt_metal/hw/inc/api/numeric/float32.h#L18-L61)
  `float32_greater`: "NaN is never greater than anything" (returns false if either operand is NaN); `±0` compare equal.
- [bfloat16.h#L66-L92](https://github.com/tenstorrent/tt-metal/blob/9fa00fce13cda1538f0130695576408ff5b05665/tt_metal/hw/inc/api/numeric/bfloat16.h#L66-L92)
  `bfloat16_greater`: no NaN and no zero handling; sign-first ordering, so `+0 (0x0000)` is strictly greater than `-0 (0x8000)`.

Consumers: [argmax_common.hpp#L130-L137](https://github.com/tenstorrent/tt-metal/blob/9fa00fce13cda1538f0130695576408ff5b05665/ttnn/cpp/ttnn/operations/reduction/argmax/device/kernels/argmax_common.hpp#L130-L137)
(`update_max_if_greater`, strict greater only) and `#L218-L232` (`process_core_data`, tie test is a raw `val == max_val`),
used by `reader_argmax_interleaved.cpp`, `reader_argmax_interleaved_multicore.cpp`, `argmax_tile_h_col.hpp` and
`argmax_tile_layout.hpp`.

The registered golden is `torch.argmax`
([reduction.py#L801](https://github.com/tenstorrent/tt-metal/blob/9fa00fce13cda1538f0130695576408ff5b05665/ttnn/ttnn/operations/reduction.py#L801)),
which treats NaN as the maximum (consistent with `torch.max` propagating NaN) and returns the first index among equal
maxima, with `-0.0 == +0.0`.

This is a source-level analysis; the comparators are plain integer C++ and the replay is a line-for-line port, so the
device result is the replay result.
