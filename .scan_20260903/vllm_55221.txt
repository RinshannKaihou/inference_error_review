### 55221 [open] [Bug]: GLM-5.3-Flash: fp8 KV cache rejected by SM90 sparse MLA plan(), and the indexer prefill workspace is sized in tokens
### Your current environment

<details>
<summary>Details</summary>

vLLM `main` at `98ed0856f` (right after #53906 landed), 2x H200 NVL (SM90), TP2,
CUDA 13.0, FlashInfer 0.6.18. Model: GLM-5.3-Flash NVFP4
(`LibertAIDAI/GLM-5.3-Flash-NVFP4`), `--max-model-len 1048576`, MTP k=3, CUDA graphs on,
CPU offload connector with a 256 GiB region.

</details>

### 🐛 Describe the bug

Two independent bugs hit on the same deployment. Both are in code that came in with
#53906; both are still on `main`.

**1. `--kv-cache-dtype fp8` cannot start on `FLASHINFER_MLA_SPARSE_SM90`.**

The fp8 KV cache is allocated as `uint8` storage and `run()` views it as
`float8_e4m3fn`, but `FlashInferMLASparseSM90Builder` hands `plan()` the storage dtype
(`vllm/v1/attention/backends/mla/flashinfer_mla_sparse_sm90.py`, the `_SM90State(...)`
construction). The wrapper rejects it:

```
ValueError: MLA kv_data_type torch.uint8 is not supported
```

Startup dies there. Dropping `--kv-cache-dtype fp8` avoids it at the cost of 1.78x less
KV capacity (2,532,577 tokens instead of 4,503,445 on this hardware).

**2. The indexer prefill workspace is sized in tokens, but its KV is pool-granular.**

`vllm/models/glm5next/nvidia/attention.py:303` takes
`get_max_prefill_buffer_size(vllm_config)` as-is. That helper returns a token count
(`max_model_len * 40` entries of 132 bytes), while this indexer's spec carries
`compress_ratio == index_kpool` and `split_indexer_prefill_chunks()` is fed compressed
sequence lengths. `vllm/models/deepseek_v4/attention.py` already divides by
`compress_ratio` at the same call site.

At `--max-model-len 1048576` with `index_kpool = 4` this reserves ~5.16 GiB per GPU
during the memory profile and locks it for the process lifetime, straight out of the KV
budget. Right-sizing it here moves available KV memory from 29.44 GiB to 32.06 GiB and
the KV pool from 4,503,445 to 4,904,494 tokens, with needle retrieval on 1M-token
prompts unchanged at 4/4. Originally reported by @nood-co1 in the #53906 thread; #51252
fixes the neighbouring builder-side budget for DeepSeek and composes with this.
