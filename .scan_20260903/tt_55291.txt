### 55291 [closed] ttnn.hardswish_bw takes the wrong branch at exactly x = ±3 and uses 0.3333 for 1/3
**Component / Area:** ttnn eltwise unary backward (composite), `hardswish_bw`

**Issue Type:** Bad Outputs

## Summary

`hardswish_bw` is composed as
([unary_backward.cpp#L923-L945](https://github.com/tenstorrent/tt-metal/blob/9fa00fce13cda1538f0130695576408ff5b05665/ttnn/cpp/ttnn/operations/eltwise/unary_backward/unary_backward.cpp#L923-L945)):

```cpp
where(lt(input, -3.0f), 0.f,
      where(le(input, 3.0f), grad * (input * 0.3333f + 0.5f), grad))
```

PyTorch's reference kernel
([aten/src/ATen/native/cpu/Activation.cpp, hardswish_backward_kernel](https://github.com/pytorch/pytorch/blob/main/aten/src/ATen/native/cpu/Activation.cpp))
is

```cpp
if (self <= -3) return 0;
else if (self < 3) return grad * (self / 3 + 0.5);
else return grad;
```

Both boundary comparisons are inverted relative to the reference: ttnn is `<` at -3 where torch is `<=`, and `<=` at +3
where torch is `<`. The registered golden for this op is torch autograd, so the op and its golden disagree at exactly
`x = ±3`. Those values are bf16-exact and ordinary in activation tensors, so exact hits are not rare.

A secondary defect on the same line: the slope constant is `0.3333f` while the forward `hardswish` kernel uses the
correctly rounded `1/6` (`hardsigmoid_init` loads `0.1666666716337204f`). In fp32 this costs 336 to 2097 ULP everywhere in
`(-3, 3)`; at `x = 2.5` the op returns `1.33325` for `1.3333333`.

This is a source-level analysis with a host replay; I do not have a card. The comparisons and constants are exact, so the
device result at `±3` is the same as the replay.

## Observed vs expected (identical in fp32 and bf16, since ±3 is exact in both)

| x | grad | `hardswish_bw` now | torch autograd | abs error |
|---|---|---|---|---|
| -3 | 1 | -0.4999 | 0 | 0.50 |
| +3 | 1 | 1.4999 | 1 | 0.50 |
| -3 | 2 | -0.9998 | 0 | 1.00 |
| +3 | -2 | -2.9998 | -2 | 1.00 |
| 2.5 | 1 | 1.33325 | 1.3333333 | 8.3e-5 |

At `x = -3` the returned gradient even has the wrong sign (negative where the reference is exactly 0).
