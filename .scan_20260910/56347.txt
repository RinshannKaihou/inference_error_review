### Your current environment

- 4x AMD Instinct MI355X (gfx950), TP4, V2 model runner; ROCm 7.2.3 in the container (host 7.1.1)
- `vllm/vllm-openai-rocm:nightly-2a02f6efe319c885e3ccbcecde402e0028f9ec1e` plus a python overlay from the head of #56214, which is what supplies DeepSeek-V4.1 on ROCm
- `deepseek-ai/DeepSeek-V4.1-Flash` (`DeepseekV41ForCausalLM`), `cudagraph_mode=FULL_DECODE_ONLY`

### 🐛 Describe the bug

With FULL decode CUDA graphs, the engine segfaults **deterministically on the 3rd decode token of the first request**. `--no-async-scheduling` eliminates it.

```
!!!!!!! Segfault encountered !!!!!!!
  File "<unknown>", line 0, in 0xffffffffffffffff
Worker proc VllmWorker-0 died unexpectedly   ->   EngineDeadError
```

#### Reproducer

```bash
vllm serve /path/to/DeepSeek-V4.1-Flash \
  --tokenizer-mode deepseek_v41 --tensor-parallel-size 4 \
  --gpu-memory-utilization 0.9 --moe-backend aiter_triton_mxfp4_bf16 \
  --compilation-config '{"cudagraph_mode":"FULL_DECODE_ONLY"}'

for mt in 1 2 3; do
  curl -s -o /dev/null -w "max_tokens=$mt http=%{http_code}\n" \
    localhost:8000/v1/completions -H 'Content-Type: application/json' \
    -d "{\"model\":\"DeepSeek-V4.1-Flash\",\"prompt\":\"word word word word word word word word word word\",\"max_tokens\":$mt,\"temperature\":0,\"ignore_eos\":true}"
done
```

```
max_tokens=1 http=200
max_tokens=2 http=200
max_tokens=3 http=500     <- all four workers segfault
```

Prompt length is irrelevant (11 tokens and 1024 tokens behave identically). With `--no-async-scheduling`: the ladder up to `max_tokens=256`, a 1001-token prompt generating 512, and `vllm bench serve` at concurrency 1/8/32/64 all pass with 0 failed requests.

`cudagraph_mode=NONE` also avoids it, but costs ~3.5x on decode (149 ms/token vs 43 ms at concurrency 1).

#### Why the 3rd token

Async scheduling is on by default and sets `batch_queue_size = pp_size + 1` (2 here, with pipeline-parallel size 1), and `vllm/v1/engine/core.py` returns early while the queue is not full:

| engine iteration | work | blocks on |
|---|---|---|
| 1 | prefill (eager) | nothing — queue < 2 |
| 2 | decode 1 (graph replay) | step 1 |
| 3 | decode 2 (graph replay) | step 2 |

Iteration 3 is the first whose host-side input preparation overlaps an **unretired graph replay**; with `max_tokens=2` it never happens. That also explains FULL vs NONE: eager issues thousands of launches so the host stays behind the GPU, while `graph.replay()` is a single launch returning in microseconds, letting the host run ahead of ~10-30 ms of live work.

#### Evidence it is runner-level

Every model-level change I tried left the failure on exactly the same token: disabling the model's side streams, bounding every index in the sparse-indexer decode path, forcing the heavy indexer to run eagerly (256 steps pass), removing it from the captured graph entirely (still crashes), widening `UvaBufferPool`'s round-robin depth, and `VLLM_DEBUG_WORKSPACE=1` showing no post-capture workspace resize. It is not sequence-dependent either — an 11-token and a 1024-token prompt give opposite compressed-KV parity on the crashing step yet die at the same replay count. Standalone microbenches (UVA pinned-host reads inside a graph, 24 graphs sharing a pool with intra-capture allocation, a 4 GiB pinned UVA table, the real `rocm_sparse_attn_decode` across a growing context, the real `_engram_lookup_kernel` with out-of-range ids) all return correct results, so no individual primitive is broken.

#### Suspected unsynchronised access

Not pinned, hence a report rather than a patch. The strongest lead is an asymmetry in the function that replays graphs — `run_fullgraph` guards exactly one producer:

```python
# vllm/v1/worker/gpu/cudagraph_utils.py
# ... Without this, replay could overwrite static buffers
# while those copies are still in flight.
get_offloader().sync_prev_onload()
self.graphs[desc].replay()
```

`output_copy_stream` gets no equivalent: `vllm/v1/worker/gpu/async_utils.py` records `copy_event` on `copy_stream` but only synchronises it inside `get_output()`, so the main stream never waits on it. Concretely: step N-1's D2H copies can still be reading the graph's static output buffers when iteration N+1 replays into those same buffers. (`get_output()` does host-sync, so the window is bounded by `batch_queue_size` — it is not unsynchronised forever, just not synchronised against the *replay*.)

#### Possibly broader

Nothing here is DeepSeek-specific, and it is likely **not ROCm-specific either** — I have only tested ROCm, so the title tag reflects where I reproduced it, not where I believe it is scoped.

`DeepseekV41ForCausalLM` has no `@support_torch_compile`, and it is **not** in `DEFAULT_BREAKABLE_CUDAGRAPH_ARCHITECTURES` on main either, so it is forced onto FULL graphs on CUDA as well; ROCm additionally returns an empty set from `default_breakable_cudagraph_architectures()`. Most other models are torch-compiled and run PIECEWISE graphs, which issue many launches and keep the host behind the GPU. I have not tried the repro on NVIDIA.

#52644 may be the same cause with a different symptom (DeepSeek V4 accuracy drop, same platform/runner/graph mode, also clean under eager) — a race here corrupts values as readily as pointers. #55095 would default DeepSeek V4 MRV2 on gfx950 to `NONE` because of #52644, giving up the ~3.5x rather than the overlap.
