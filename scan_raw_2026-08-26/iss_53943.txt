### 🐛 Describe the bug

We built PR #53906 for ROCm to see where AMD support for GLM-5.3-Flash actually stands. Summary: **the platform guard is not the real blocker — a stale `forward_hip()` is.** Sharing the details in case they save someone a cycle.

#### 1. The build itself is clean

`VLLM_TARGET_DEVICE=rocm` with `PYTORCH_ROCM_ARCH=gfx950` completes with `rc=0`. Both `Glm5NextForCausalLM` and `Glm5NextForConditionalGeneration` register, and `current_platform` reports `rocm`.

#### 2. The guard rejects ROCm at import time

`vllm/models/glm5next/__init__.py`:

```python
if current_platform.is_rocm() or current_platform.is_xpu():
    raise NotImplementedError(
        "GLM-5.3-Flash currently supports NVIDIA SM90 and above only.")
```

This fires before any model code executes. Worth noting what sits underneath it: grepping `vllm/models/glm5next/` for `flashinfer|tilelang|trtllm|flashmla` returns **zero** hits, and the only kernels there are `@triton.jit` (`ops/fused_eh_norm.py`, `ops/kpool_compress.py`). So the guard looks precautionary rather than load-bearing.

#### 3. With the guard removed, weight loading succeeds

```
INFO [default_loader.py:430] Loading weights took 61.57 seconds
```

Served with `--tensor-parallel-size 8 --kv-cache-dtype fp8 --max-model-len 131072 --max-num-seqs 64 --gpu-memory-utilization 0.85 --trust-remote-code`.

#### 4. The actual blocker

```
RuntimeError: Worker failed with error
'SparseAttnIndexerKpool.forward_hip() got an unexpected keyword argument 'gate_score''
```

In `vllm/model_executor/layers/sparse_attn_indexer_kpool.py` the three dispatch paths have diverged:
